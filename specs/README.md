# specs/

Clean specifications that implementers code from. Each spec is derived only from allowed sources
(see `../CLEANROOM.md`).

**Reading the evidence.** The "reference stack" is an earlier test server and client that the project built and ran only to compare behaviour; it is not published. Grades named REFERENCE record what it did. Rule values are never taken from it. Paths such as `captures/...`, `reports/...`, `staging/...` and `evidence/...`, and the `decompiler` trees, name files in the maintainers' evidence archive. That archive is not published, because it holds bytes and analysis output of the 2009 client.

## Index (state after spec-fold-8, 2026-10-25; spec-fold-9 corrections recorded in the last row of "Later additions")

Grades. Each file's header defines its own; the capture grades added by spec-fold-4 mean:
- **PROVEN-CAPTURE**: the real 2009 client's own bytes or behaviour in a packet capture (tdm1, tdm2, tdm4 of 2026-10-25, `captures/<id>/capture.jsonl`). 2009 evidence, never downgraded.
- **REFERENCE-CONFIRMED**: a server -> client form written by the reference stack that parses exactly under the spec and was accepted by the real client (its next messages could only follow a
  successful handling). It shows what the client accepts, not what a 2009 server sent (`REFERENCE_TESTING.md`).
- **REFERENCE**: what the reference stack did, recorded for comparison; never a rule value.
- REFERENCE-CONFIRMED in the spec-fold-3 "Appendix O" of the UDP specs means the older, weaker thing: a `dc-botclient` run against the reference stack agreed with the text; it is not evidence about the real client.
- **D** (added by spec-fold-5): DeCombat design, a `DC_DEFAULTS.md` row (PROPOSED unless approved) that our servers follow where the 2009 evidence leaves a choice; its test state is TESTED (a crate
  test) or RUN (a loopback run of our own stack). Never 2009 evidence. The spec-fold-5 fold records are the "Appendix F" sections (DSERVER_PIPE: section 13; PROTOCOL_2009: 7.2; RENDER_2009:
  Appendix M; FMT_DTX: section 10). The spec-fold-6 records are the "Appendix G" sections (S2C, C2S, UDP_SESSION_2009_B, GAME_MODES) and DSERVER_PIPE section 14,
  RENDER_2009 Appendix S, FMT_LTB section 15, FMT_RENDERSTYLE_2009 section 12, GLOSSARY_UDP S.F.1. The spec-fold-7 records are the "Appendix H" sections (S2C, C2S, GAME_MODES,
  UDP_SESSION_2009_A, UDP_SESSION_2009_B, UDP_TRANSPORT_2009, RENDER_2009, MOVEMENT_2009); in `../docs/` they are FIRETEAM_AI_DESIGN section 10 and VISIBILITY_CULLING_DESIGN
  section 10 (the implementation record). The spec-fold-8 records are the "Appendix I" sections (S2C, C2S, UDP_SESSION_2009_A, UDP_SESSION_2009_B, UDP_TRANSPORT_2009,
  MOVEMENT_2009, GAME_MODES, RENDER_2009, AUDIO_2009, HISEC_2009) and FIRETEAM_2009 section 5.3.
- **CONFIRMED** (used in RENDER_2009 4.2 / 4.3 since spec-fold-7): an instruction read in our own disassembly **and** the data value read from the user's ROM file
  (render-playerview's grade); 2009 evidence of the DISASM kind.

Addenda marked "stub" were applied into their base spec and keep only the applied / not-applied record. The `CAPTURE_*` and `REFERENCE_*` files are evidence records and are kept in full. Append new
rows at the end of the "Later additions" table; the two tables above it are rewritten only by a spec-fold.

## Two-person rule
The spec author is never the implementer of the same spec. The implementer codes only from the spec and allowed
sources; discrepancies go back to the author, not into silent guesses.
