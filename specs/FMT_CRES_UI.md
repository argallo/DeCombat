# FMT_CRES_UI: CRes.dll resource tables, UI layout data and font set of the 2009 client

- Scope: what the 2009 CShell.dll reads from `Game/CRes.dll` (PE resource tables) and from the attribute text
  tables that carry screen and HUD layout; the font files requested from `FONTS.rez`; the HUD element set.
  Not covered: widget rendering, texture formats (see FMT_DTX), the attribute text grammar beyond what layout needs.
- Evidence sources: decompiler output of the 2009 `CShell.dll` (`cshell+0xRVA`; image base 0x37100000, so decompiler
  `FUN_372d2cb0` is `cshell+0x1d2cb0`) and `Engine.exe` (`engine+0xRVA`; image base 0x00460000), capstone
  disassembly of the ROM binaries (read-only) for code that decompiler did not split into functions, read-only scans
  of the user ROM with own scratch walkers in `staging/fmt_cres_ui/` (built on
  `evidence/rezls.py` and `evidence/romdata.py` `entry()`), public formats: PE/COFF `.rsrc` and
  `RT_STRING` block layout (PUBLIC: Microsoft PE format documentation; `LoadString`/`FormatMessage` reference),
  TrueType/TTC (PUBLIC: OpenType specification, `name` table and TTC header), Win32 GDI `LOGFONT`,
  `AddFontResource`, `CreateFontIndirect` (PUBLIC: Win32 API reference).
- Status: DRAFT (static analysis only; nothing live-tested against the 2009 client)
- ROM data policy: no strings, rows or values from the ROM are reproduced. A string is referenced as
  `sha:<sha256[:16]>/<len>` of its bytes (as stored, without terminator), mostly together with the RVA of the
  literal inside CShell/Engine so that an implementer can read it from the user's own binary at run time (the same
  model `ca_rom::crypt_key` uses). Numbers below are counts, sizes and ranges.
- Companion table: `FMT_CRES_UI_keys.tsv` (same directory) lists every section family and key of the layout table
  (section 6.2) by sha id, with the CShell literal RVA when one exists and the value-type histogram. It is
  generated by `staging/fmt_cres_ui/butelay.py --tsv` and contains no ROM text.

Names in this spec (`ui_strings`, `layout_table`, `screen_pages`, widget kind names, HUD element names) are ours.

## 3. How CShell loads CRes resources

### 3.1 Loading the module (engine side)

- engine+0x3d970 (client shell DLL init): after CShell.dll is located and loaded into slot `+0x6ec` of the engine
  client object, the engine resolves the resource DLL by name `sha:f83476eb0998f836/8` (literal engine+0x2176cc)
  through the same "copy file out of the resource archive or game folder" helper engine+0x3d180, then loads it with
  the module loader engine+0x4b00 into slot `+0x6e4`. Failure releases CShell and fails client init.
- Slot `+0x6e8` (a second, localized resource module) is only cleared (engine+0x3d970, engine+0x193b0) and
  released (engine+0x14bf0); nothing in the 2009 engine loads it.
- engine+0xb8c50 is the engine's "get named handle" service. Query `sha:ce77382e375c026e/14` (literal
  engine+0x21f6ec) returns slot `+0x6e4`; `sha:80080a076f8581ff/15` (engine+0x21f6dc) returns slot `+0x6e8`
  (always null in 2009); other names return the main window, the CShell module or the D3D device.
- CShell calls that service through the engine interface table entry at byte offset 0x308 (global client
  interface pointer at cshell VA 0x37560ea8).

### 3.2 The eight string accessors (CShell)

All eight first query the resource module handle (3.1) and return an empty string when it is null. "static" means a
single shared buffer of 0x800 characters that the next call of the same width overwrites.

| cshell RVA | width | buffer | formatting | direct call sites (E8 scan) |
|---|---|---|---|---|
| 0x1a00b0 | ANSI | caller buffer, size | `FormatMessageA(FROM_STRING)` with caller varargs | 30 |
| 0x1a0150 | ANSI | caller buffer, size | none (`LoadStringA`) | 87 |
| 0x1a0190 | ANSI | static (VA 0x37597520) | FormatMessage with varargs | 3 |
| 0x1a0230 | ANSI | static (VA 0x37597520) | none | 87 |
| 0x1a0280 | UTF-16 | caller buffer, size | `FormatMessageW(FROM_STRING)` with varargs | 33 |
| 0x1a0330 | UTF-16 | caller buffer, size | none (`LoadStringW`) | 33 |
| 0x1a0370 | UTF-16 | static (VA 0x37596520) | FormatMessage with varargs | 0 (1 in the decompiler output) |
| 0x1a0420 | UTF-16 | static (VA 0x37596520) | none | 339 |

The formatted variants load into a private 0x800-unit stack buffer first and then format into the destination; when
`LoadString` returns 0 the destination stays empty. Total: 612 direct call sites (decompiler output shows 631 textual calls);
477 pass the id as an immediate (330 distinct ids), 135 compute it at run time (tables or `base + index`).
No CShell code reaches the CRes module except through these eight accessors: the only `FindResource` user
(cshell+0x10d440) opens an arbitrary file as a data-file module (`LoadLibraryEx`, flag 2), and the `LoadCursor`
sites use the system arrow (cshell+0x111590) or a caller-supplied instance (cshell+0x10ffb0; that instance is
UNPROVEN to be CRes). Whether the one cursor resource is ever used is UNPROVEN (no reference found).

Rust model (`ui_strings`): load the `RT_STRING` blocks of the user's CRes.dll with a PE resource reader (no Win32
dependency); `get(id) -> Option<&str>` (UTF-16 decoded) and `format(id, args)` implementing the FormatMessage
insert grammar `%n`, `%n!printf-spec!`, `%%`, `%n` newline escapes (PUBLIC). Missing id = empty string, never an
error (matches the 2009 behaviour).

### 3.3 Classification method for the id table

`staging/fmt_cres_ui/cresids.py` scans `.text` for E8 calls to the eight accessors and takes the last `push imm`
before the call as the id (cdecl, first argument pushed last); `cresmap.py` buckets ids by range and owner class
(`classmap.py`: RTTI type descriptor -> complete object locator -> vtable -> member functions). Owner names were
used only to write the "used by" column in our own words.

## 5. Layout initialisation and load order in CShell

Objects: the layout manager is a single global (pointer at cshell VA 0x37560d70). Its constructor chain is
cshell+0x4bc60 (derived, installs vtable cshell+0x3d0f34) -> cshell+0x1ce730 (base, vtable cshell+0x3ed318, built on
the generic attribute-table object cshell+0x1a2da0). Derived vtable slot 0 (cshell+0x4bcc0) forwards to the base
init cshell+0x1d2cb0 and normalises the result to 0/1.

Order (each step must succeed or interface init aborts through the engine error service):

1. engine+0x3d970: load CShell.dll and CRes.dll (section 3.1).
2. Interface manager init (cshell+0x1b7ff0). At cshell+0x1b8596 it calls layout-manager slot 0 with the
   `layout_table` path.
3. cshell+0x1d2cb0, layout init:
   1. parse `layout_table` with the generic attribute loader cshell+0x1a35f0 (decrypts in memory, same cipher);
      returns 0 on failure.
   2. count numbered HUD sets: probe sections `HUD set prefix + n` (prefix literal cshell+0x3d0f60,
      `sha:9b19ccce0890983f/9`, format `%s%d`, first probe `%s0`) until the first missing section; count -> object
      `+0x15ac`.
   3. count vector-font entries: in section `sha:3680fcad01f4bfc6/5` (cshell+0x3ed06c) probe key
      `sha:54ddfbaef74b42f8/10` (`...%d`, cshell+0x3ed074) from 0 upward; count -> `+0x15b0`.
   4. count system font records: sections `sha:523251e8d40f73d7/7` (cshell+0x3ece6c) + n; count -> `+0x15b4`.
   5. read light records: sections `sha:dbcd5e7bb7a0f538/5` (cshell+0x3ed8e4) + n, each parsed by cshell+0x1c7be0
      into a list at `+0x15bc` (failed parses are dropped, numbering continues).
   6. read interface FX records: sections `sha:adf02dd669bdb324/2` (cshell+0x3ed8e0) + n, parser cshell+0x1c7d50,
      list `+0x15cc`.
   7. read screen transitions: sections `sha:2fe70464aadf5873/10` (cshell+0x3ed8d4) + n; each has a from-screen and
      a to-screen key (`sha:5e7f9ca474b2a86a/14`, `sha:c3b94c0e41ae57d3/12`) holding screen names that are mapped
      to screen ids by cshell+0x64780 (name -> id, 999 when unknown, stored as 0), then sub-records 0, 1, ... parsed
      by cshell+0x1c31e0 into list `+0x15dc`. The 2009 ROM has 0 transition sections.
   8. install the attribute cipher key (`+0x15a4` = literal cshell+0x3e9abc; cshell+0x19dec0).
   9. parse `screen_pages` (cshell+0x1d2670, section 6.3).
   10. parse `preload_list` (cshell+0x1d1d90, section 6.4).
4. cshell+0x1b85bb: compute the packed background colour from the base section (cshell+0x1c7f00: vector key
   `sha:c86f21073a9da674/9` of section `sha:d310cd72eb5bdab5/11`, three float components packed to 0x00RRGGBB) into
   cshell VA 0x37598918.
5. Interface resource manager init cshell+0x1c2120: reads CRes strings 265 and 266 as decimal integers (atoi,
   fields `+0x38`, `+0x3c`; meaning UNPROVEN), then builds the system font table (cshell+0x1c1e70, section 7.1),
   then cshell+0x1bef80 stores the UI scale: screen width / 1024 and screen height / 768 (constants 0.0009765625 and
   0.0013020834), i.e. every layout coordinate is authored for a 1024 x 768 virtual screen.
6. Screen manager init (interface vtable `+0x68`, then its slot 1); failure message logged.
7. HUD manager init (interface vtable `+0x64`, then its slot 0 = cshell+0x45c30, section 8).

Rust load order: `ui_strings` (CRes) -> `layout_table` -> `screen_pages` -> `preload_list` -> fonts -> screens
-> HUD. Coordinates are virtual 1024 x 768 and scaled per axis.

## 6. Layout data model

### 6.1 Value grammar of `layout_table` (attribute text)

`layout_table` uses the common attribute grammar (`[section]` headers, `key = value` lines; the generic loader
cshell+0x1a35f0 and the typed getters below). Typed getters check a stored type tag and return the caller default on
mismatch (setting a "found" flag at object `+0x11` to 0):

| tag | getter (cshell) | value form in the text | Rust type |
|---|---|---|---|
| 1 | 0x1990c0, 0x199110 | decimal integer | `i32` |
| 2 | 0x199170, 0x1991c0 | (UNPROVEN form; 4 uses in CShell) | `u32` |
| 3 | 0x199270 | (UNPROVEN; 2 uses) | `u8` |
| 4 | 0x1992d0, 0x199320 | boolean | `bool` |
| 5 / 6 / 1 | 0x199380, 0x199430 | real (double or float), integers accepted | `f64` |
| 7 | 0x1994f0, 0x199540, 0x1995b0 (copy to buffer, default string) | `"text"` | `String` |
| 8 | 0x1996a0, 0x1996f0 | `(a, b, c, d)` integer 4-tuple (rects) | `[i32; 4]` |
| 9 | 0x199790, 0x1997e0 | `(x, y)` integer pair (positions, sizes) | `[i32; 2]` |
| 10 | 0x199870, 0x1998c0 | `<r, g, b>` real 3-vector (colours 0..255, light vectors) | `[f64; 3]` |
| - | 0x199e30 | existence test of a section or of a key in a section | `bool` |

Observed value forms over `layout_table` (key occurrences, `FMT_CRES_UI_keys.tsv`): integer pairs 1142, integers 817,
strings 711, real 3-vectors 142, reals 146, integer 4-tuples 74.

### 6.2 `layout_table` sections and lookup rules

Lookup rules the Rust UI must reproduce:

- Per-screen key: section = the screen's name from the screen id table (cshell+0x64770: `id * 32 + VA 0x37542f68`,
  30 entries of 32 bytes, index 0 is the fallback "generic screen" section `sha:8ec627f6f21b861c/13`). The accessors
  cshell+0x1c5e70 (title font), +0x1c5ed0 (title size), +0x1c5f30 (font index), +0x1c5f90 (font size), +0x1c5ff0
  (item spacing), +0x1c6050 (item alignment), +0x1c60b0 (music intensity) first test the key in the screen's section
  and fall back to the same key in section 0. The generic accessors cshell+0x1c6110 (int), +0x1c6140 (real) and
  +0x1c6180 (string) read a caller-named key in the screen's section without fallback; cshell+0x1c6250 reads a
  caller-named string key from section 0 only.
- Base constants: fixed section `sha:d310cd72eb5bdab5/11` (cshell+0x3ecf68), accessors cshell+0x1c5c90..0x1c5e55
  and +0x1c7e83..0x1c8003.
- HUD keys: section = HUD set prefix + selected index (section 8.2); when a key is absent there, the HUD accessors
  (example cshell+0x4bce0) fall back to set 0 (`sha:089cb83a2538a401/10`, cshell+0x3d3478).
- Name -> screen id: cshell+0x64780 compares case-insensitively against the 30 table names, 999 if none.

Section families (digits = numbered sections; "screen n" = index in the screen id table; `none` = no literal of that
section name in CShell, i.e. not opened by name). 103 families, 159 sections, 3275 key lines.

### 6.3 `screen_pages` grammar (front-end widget layout)

Parser cshell+0x1d2670 (argument ignored, opens the `screen_pages` literal itself through the engine file service at
interface pointer VA 0x375964f4, vtable `+0x2c`):

1. Read the whole entry; when the cipher key is installed (always, step 3.8 above) decrypt it in memory
   (cshell+0x19e0c0, 8-byte blocks, plain tail).
2. Copy it to a temporary stream dropping every CR that is directly followed by LF.
3. Pre-allocate one prototype record per widget kind (sizes in the table below) and a page-holder object.
4. Read lines (max 0x104 bytes, `fgets`) until a line starting with the page-list end tag
   `sha:db717ba76600179a/21` (cshell+0x3ed5b0, compared case-insensitively over 21 chars). Empty lines are skipped.
   A line that starts (case-insensitively, over the tag length) with one of the 20 page tags of the page tag table
   (pointers at cshell VA 0x37555a38, `.data` cshell+0x455a38; tags are `[[name]]`) starts a page: cshell+0x1d2260
   parses it, cshell+0x1d1430 stores it. Lines matching no tag are ignored.
5. Page body (cshell+0x1d2260): the end tag is the page tag with `_end` inserted before the closing `]]`. Inside, a
   line starting with key `sha:72926e1ab2dca5d3/11` (cshell+0x3ed59c) is `screen_name = "<name>"` (sscanf `%s %s %s`,
   quotes stripped): the page's own name. Widget blocks start with a kind tag (case-insensitive prefix compare) and
   end with the matching end tag:

   Key spelling in the ROM varies in case and wording between records of the same kind, which is harmless for the
   2009 client and must be harmless for ours. Values must not contain spaces (the `%s` token ends at a space).

## 7. Font set

### 7.1 System font table (the font table the 2009 UI actually uses)

- Records: sections `sha:523251e8d40f73d7/7` (cshell+0x3ece6c) + n, n = 0 .. count-1 (count from layout init step
  3.4; 27 in the ROM).
- Build: cshell+0x1c1e70 (called from the resource manager init cshell+0x1c2120). Requires the font manager
  interface (cshell VA 0x37598a98) and the layout manager. For each record:
  1. name = string key `sha:dcd1d5223f73b3a9/4` (cshell+0x1c35c0). Empty -> log and skip (a placeholder name is
     formatted but nothing is added).
  2. request = cshell+0x1c6380 into a 0x130-byte request block:

| request offset | source key (section = this record) | literal | type |
|---|---|---|---|
| 0x000 (0x104 bytes) | file in a rez archive, may be empty | `sha:e316d2ad49b2586a/8` cshell+0x3dc18c | string |
| 0x104 (0x20 bytes) | face name | `sha:2cfc59e319387a98/8` cshell+0x3ed0c4 | string |
| 0x124 | width | `sha:3019947b6daf18b0/5` cshell+0x3ed0bc | int, default 0 |
| 0x128 | height | `sha:bfe2eca401797325/6` cshell+0x3ed0b4 | int, default 0 |
| 0x12c | bold | `sha:94fee62e68e257c0/4` cshell+0x3ed0ac | int != 0 |
| 0x12d | italic | `sha:9bf37cb58a694456/6` cshell+0x3ed0a4 | int != 0 |
| 0x12e | underline | `sha:02f843261112c2d8/9` cshell+0x3ed098 | int != 0 |
| 0x12f | always 0 | - | - |

     The request is valid when file or face is non-empty. An invalid request logs and writes the 5-character face
     `sha:aac910161f16402c/5` into the local request, but **does not create a font** (no entry is added).
  3. font manager slot `+0x14` (get font for request); null -> log, no entry.
  4. success -> append `(name, font)` as a 0x20-byte entry to the table at resource manager `+0x18`
     (cshell+0x1c1c80).
- Lookup by index: cshell+0x1c07b0 `(index, allow_default)`: index past the end returns null, or entry 0 when
  `allow_default` (logged). Because failed records add no entry, a failure shifts every later index (behaviour to
  copy only if the Rust UI wants bug-compatibility; recommend: keep a slot per record and fall back to entry 0).
- Engine side of "get font" (engine+0xead10): if the file field is non-empty, engine+0xe0ca0 makes the file available
  on disk (copy-out helper) and installs it process-wide with `AddFontResourceA` (engine+0xdf030). The logical font
  (engine+0xe77b0) is: `lfHeight` = height, `lfWidth` = width, escapement 0, orientation 0, `lfWeight` 400, or 700
  when bold is set **and** an engine-side option (interface at engine+0xe1060, slot `+8`) is true, `lfItalic`,
  `lfUnderline` from the request, strike-out 0, charset 1 (GDI default character set), out precision 0, clip precision 0,
  quality 4 (`ANTIALIASED_QUALITY`), pitch-and-family 2 (`VARIABLE_PITCH`), face = face name (also widened for the
  wide variant); engine+0xeac00 creates it with `CreateFontIndirectA` or `CreateFontIndirectW` (PUBLIC: GDI).
- ROM counts: 27 records; 6 distinct keys used; 11 records name a font file, 9 of those files exist in FONTS.rez and 2
  name a file that is not in the ROM (`sha:359a517e6bc696ab/10`; the 2009 client then depends on the system having
  that face installed: UNPROVEN what happens when it is missing); 16 records use a system face only. Bold is set in
  17 records. Heights: 9 distinct values, 14..56. Of the 11 file-backed records, 7 face names match a family or full
  name in the file's `name` table (ids 1 and 4), 2 do not (UNPROVEN: GDI then substitutes), 2 have no file.

Users of the font index: `font_index` of `screen_pages` buttons and text widgets (observed range 0..25, all below
27), the per-screen font key (cshell+0x1c5f30, read by the widget builders cshell+0x1abe10, +0x1ac080, +0x1ac390,
+0x1b0130, which resolve the index through cshell+0x1c07b0), the base help font (cshell+0x1c5c90, caller

miscellaneous section (cshell+0x1c6610; no direct caller found) and HUD keys that name fonts.

### 8.2 HUD layout set selection

cshell+0x26b380 calls cshell+0x19fde0 with the HUD prefix `sha:9b19ccce0890983f/9`: it looks the name up as an
engine console variable (engine interface slot `0x104`, value via slot `+0x5c`), rounds it to an integer, default 0,
and stores it as a byte at HUD manager `+4`. HUD keys are then read from section prefix + index with fallback to
set 0 (6.2). The ROM has exactly one numbered set (set 0, 944 keys) plus the base HUD section (4 keys), so every
index resolves to set 0.

HUD texture paths named by `layout_table` live in the HUD rez files of the ROM (path folder = rez file stem); section 9 gives the
resolution counts.
