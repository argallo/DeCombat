# MAPKIT_VOCAB.md: the DeCombat map vocabulary

Status: binding since 2026-11-01 (docs/MAPKIT_PLAN.md §4, D1; rules MAP-1..MAP-3 in `DC_DEFAULTS.md`). A community
map built by dc-mapkit writes these class and property names into its version-85 world file; the game server,
the simulation and the renderer accept them as aliases next to the ROM's hashed names. No ROM class or property
name is ever written by the tool or committed to this tree.

The source of truth is `crates/dc-world/src/vocab.rs` (`dc_world::vocab::CLASSES`, `LEADING`); the keys the
readers match against are `crates/dc-world/src/names.rs` (`dc_world::names::*`, `dc_world::Key`). The tables under
"Generated" are printed by `cargo run -p dc-world --example vocab_md`; the test
`tests/dc_vocab.rs::vocab_doc_carries_the_generated_tables` fails when this file and the code disagree.

## Rules

- **MAP-1, the vocabulary.** Classes are `dc.<class>`; properties are short lower-case words. The ROM roles the
  vocabulary does not offer (trigger volumes, mode controllers, start-up commands, camera points, doors, switches,
  water, placed effects) have no `dc.*` name: a community map cannot place them (scope cut D12).
- **MAP-2, matching.** A reader matches a class name by the exact ROM hash and length (`sha256(name)[:8]`,
  FMT_DAT85.md §12) OR by ASCII-case-insensitive equality with the vocabulary name (`dc_world::Key::matches`). A
  property name matches by hash on every object, and by its vocabulary name only on a vocabulary object, one whose
  class is a `dc.*` name (`dc_world::Object::dc`, `names::is_dc_class`): a ROM object's properties resolve by hash
  alone, so a ROM property that happens to spell a vocabulary word is never read as that word. Property 0 / 1 / 2
  (`name`, `pos`, `rot`) are read by index (FMT_DAT85.md §6.1); their names are aliases for readers that look them
  up by name. The same word may be a different ROM property on
  different classes (`team` on a spawn or flag is the team filter, on a flag zone the zone team; `color` on a light
  is not the sprite colour; `file` on a sound is not the sprite file): the reader picks the key by class, and
  `names::keys_named` lists every key of a word. `sky_inner` is one vec3 that the readers serve as the ROM's three
  inner-percent reals; `fog_color` is one rgb (the ROM property is too) and `wind` one vec3, split into their parts
  by the evar sender. A world-settings row matched through an alias has no ROM property name to send as the
  evar's name (`evars.rs name: None`).
- **MAP-3, brushes.** A brush class (`dc.kill_volume`, `dc.hazard`, `dc.ladder`, `dc.world_model`,
  `dc.breakable`, `dc.sky_model`) links to the BSP model whose name equals its `name` exactly (bytes, FMT_DAT85.md
  §6.4); the model's `origin` equals the object's `pos` and the geometry is stored in world space, so `rot` is
  ignored on brush classes (the tool writes 0). Every brush model carries `bsp_flags` bit 1; the level model is the
  one model no object names (bit 1 clear) and there is exactly one.

Team texts are `"1"` / `"2"` (empty = any where allowed); `modes` is a comma list of the lobby's playable mode
names (`TDM, FFA, ELIM, BOMB, FLAG, ...`, `dc-config modes.playable`), empty = every mode. Box extents are HALF
extents. Paths in `file` and `model` are ROM archive paths or `@mod:<id>/assets/<rel>`.
